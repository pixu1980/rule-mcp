The four critical findings

  1. OSS-1 - three packaging manifests name three different GitHub owners. scoop says github.com/rule, winget says owner rule with github.com/rule, Homebrew says github.com/rule-mcp. All three pin 0.1.0, two carry a literal PLACEHOLDER hash, and all three point at a v0.1.0 tag that does not exist. The owner is pixu1980.
  2. OSS-2 - SECURITY.md routes vulnerability reports to a public issue. No private channel, no contact, no SLA, no embargo window, no CVE step.
  3. OSS-3 - server.json claims the io.github.rule namespace while the GitHub owner is pixu1980. The registry validates namespace ownership against the publishing account, so the file is unpublishable as written.
  4. OSS-4 - README, its npm badge and docs/01-getting-started.md sell pnpm add -g rule-mcp as the recommended install. npm view returns E404.

Two of these were reproduced rather than inferred: npm view rule-mcp returns E404, and installing the packed tarball fails with EUNSUPPORTEDPROTOCOL because "rule-mcp": "link:" sits in dependencies (OSS-5). That protocol error is also why the documented install cannot work even against a registry.

Bugs the work surfaced

OSS-31, found while validating this session's own output. rule_tool_plan_docs writes Markdown that the repository's own Prettier gate rejects. Immediately after the generator wrote the trio:

pnpm exec prettier --check docs/audits/oss.md docs/reviews/oss.md docs/plans/oss.md
[warn] Code style issues found in 3 files. Run Prettier with --write to fix.

The same command reports All matched files use Prettier code style! for the repository's other generated Markdown (docs/adr/ADR.md, docs/README.md, README.md), so the gate is sound and the generator output is what fails it. src/core/review/docs/_table.js writes rows as | a | b | with no column padding, while package.json format runs prettier --check '**/*.{js,mjs,json,md}'. tests/docs/review-docs/ holds gate, plan-checklist and sync tests but none asserts the rendered output is Prettier-clean. Every persona run therefore leaves the lint job red until someone runs pnpm format:fix, and the next generator run undoes it. This session ended by running format:fix, which is the workaround, not the fix.
