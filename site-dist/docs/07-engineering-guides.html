Engineering guides

Practical guides for working on rule-mcp itself: the engineering loop, the guardrails, the docs pipeline, and the numbers that matter. Counts here are verified by tests/docs/docs-accuracy.test.mjs against the live registries; the heavy inventories live in the generated census blocks of docs/01-, docs/02- and docs/04-.

The engineering loop

The server is deterministic and LLM-free: tools route, scaffold, validate, search, and record - they never generate prose by calling a model. Work on it follows the standard loop, enforced by the repo's own guardrails:

  1. Write the failing test first. node --test tests/<area>.test.mjs runs a single suite; pnpm test:all runs everything.
  2. Implement until the suite is green.
  3. Self-check with the repo's own guardrails: pnpm lint (eslint with --max-warnings 50) and tests/core/self-guardrails.test.mjs (the server must pass its own rule_tool_check rules - a guardrail product whose source cannot pass its checks is ignored by everyone downstream).
  4. Format: pnpm format:fix (prettier) so pnpm format stays clean.
  5. Regenerate the census when the surface changed: pnpm census updates the generated blocks in docs/01-, docs/02-, docs/04-, docs/05- (tests/docs/census-generated.test.mjs fails otherwise).
  6. Commit with a scoped conventional message: type(scope): subject (the commit-msg hook rejects scope-less subjects).

The guardrails

Guardrail rules live in src/core/guardrails/ split by domain and are applied per skill by src/core/guardrails.js (getGuardrails / checkCode).

  • Shared + quality families run on every skill: TypeScript strictness, the fingerprint family (em/en dashes, curly quotes, British -> American spellings), comment hygiene, simplicity rules, flex-first layout, and the English-only rule (en-english-only-prose: comments, identifiers and whole .md documents must be English, American spelling).
  • Domain families attach per skill: backend, database (data-*), devops, a11y (frontend/platform/ui/styleguide), framework and scaffold rules.
  • Precision is measured: tests/fixtures/guardrail-corpus.mjs feeds every rule labeled good/bad snippets; tests/core/guardrails-precision-recall.test.mjs requires 100% precision and recall per rule - a rule that fires on idiomatic code or sleeps on violations fails the suite.
  • The repo is its own first customer: tests/core/self-guardrails.test.mjs runs the JavaScript rules over src/** and fails on any violation.

The docs pipeline

Numbered docs are partly generated. scripts/reports/census/index.mjs refreshes the blocks between <!-- census:begin/end:<marker> --> markers in the numbered docs and is wired into prebuild:

  • docs/02-product-architecture.md - tool-family counts
  • docs/04-operations.md - tools in detail, resources, review personas, .roo/commands snapshot
  • docs/03-agent-instructions.md - the command surface and persona table
  • docs/05-env-variables.md - the environment registry

docs/README.md is the index. ADRs in docs/adr/ are immutable decision records (a merger or a reversal writes a new ADR). A roadmap or plan never claims a numbered slot: it is deleted when fully executed or obsolete. 01-getting-started.md is the first-run guide.

To add a surface, change the code, run pnpm census, verify tests/docs/census-generated.test.mjs and tests/docs/docs-accuracy.test.mjs, then commit - the docs follow the code instead of being remembered.

Measured numbers

  • Skills: 96 skills/*/SKILL.md documents, each registered as a rule-tool-<skill> MCP tool with full/summary/tldr/search/guardrails/check modes; 112 tools and 198 rule:// resources in total (runtime counts, see the generated blocks).

  • Skill reading is cached (LRU): a cache hit is sub-millisecond, a miss is one disk read.

  • Routing builds a deterministic BM25 index at startup; routing is measured against tests/fixtures/routing-corpus.mjs with floors on exact and top-or-alternative hits, so a new skill can only land when routing still finds the intended target.

  • Tests: the suite covers the installer (bash + PowerShell), the CLI parse surface, the guardrails corpus, the docs/census drift, the personas and the transports (stdio, SSE, HTTP, daemon, Docker).

  • Compression (pnpm report:compression, 2026-09-09) removes, by level:

    Corpus lite full ultra
    skills (89 SKILL.md) 0.06 % 1.52 % 2.02 %
    docs (17 files) 0.02 % 0.56 % 0.73 %
    real tool results (6) 0.11 % 2.03 % 2.58 %
    verbose prose (synthetic) 17.4 % 34.2 % 42.3 %

    The two rows are not in conflict. The shipped corpora are already written in the compressed style, so on them the rules measure how little filler is left; the synthetic corpus is what an uncompressed assistant answer looks like, and that is the corpus the level table describes. Guard violations are 0 at every level on all four, which is the number that has to stay 0.

    The rules are ported from the rule-caveman skill and its caveman-compress companion: the vocabulary tables, the classification guards and validate.py's structural validator. The LLM compression step is deliberately not ported - an LLM in the output path costs determinism, cacheability and the zero-dependency contract, and the guard plus per-block rollback buys the same safety for free (ADR 073).

Compression surfaces: everything the server emits to a model

The rule is one sentence: every text the server hands to a model runs through src/core/text/ before it leaves. The manifest lives in src/core/text/_surfaces.js and is pinned by src/core/text/__tests__/_surfaces.test.mjs; the table below is that manifest rendered. "Prose" surfaces shorten verbose text, keep JSON identical and never break structure (the guard errors stay 0); the documented skips say why they are not compressed.

Surface Where Status Telemetry source
tools/call results src/tools/router/_helpers.js finalize() prose caveman
resources/read bodies (text/*) src/resources/_serve.js readResource() prose caveman-resource
prompts/get bodies src/server/_prompt-handlers.js GetPrompt prose caveman-prompt
prompts/list descriptions src/server/_prompt-handlers.js ListPrompts prose caveman-prompt-list
tools/list descriptions src/tools/router/_surface.js listTools() prose none (memoized at startup)
resources/list labels src/resources/_listing.js prose (no-op on the terse set) none (ADR 077)

banners (self-update notice, resume announcement) src/tools/router/_helpers.js withBanner() prose caveman-banner

By document category, the answer to "is it compressed before it reaches a model?":

Category Status
Markdown (handoffs, docs served via rule:// text resources, the resume hook block) compressed (tool result, resource read, caveman-resume)
Skills (full body + summary resources, tool-embedded evidence) compressed (resource read + tool-result pass)
Resources read: compressed; list labels: pass-through (no-op, ADR 077)
Instructions (session/prompt directives, agent-instruction files) directives already terse by authorship; anything emitted runs the pass
Prompts get: compressed; list: descriptions compressed (ADR 077)
Tools results: compressed; list: descriptions compressed, schemas never (ADR 077)
Personas served content (plan outputs): compressed via the tool-result pass; src/roles/*.md source files stay untouched on disk

Opt-outs apply everywhere: RULE_MCP_NO_CAVEMAN=1 and RULE_MCP_CAVEMAN_LEVEL=off turn the pass off on every surface that runs it (plus RULE_MCP_NO_RESUME_HANDON for the resume block and RULE_MCP_NO_REMINDER for the reminder).

  • Startup (pnpm report:startup, 2026-09-09): warm --help 48 ms, tools list 265 ms, stdio initialize 251 ms. A cold process spends 12 ms on the entry import, 53 ms registering skills and 8 ms converting tool schemas; the second tools/list in a process is free. The compiled code cache is worth 2-6 %; the 168 ms came from what --help no longer loads (ADR 074).

Contributing

  • Read docs/README.md, then the numbered docs relevant to your change.
  • Open work is tracked in the issue tracker; plans inside the repo are deleted when fully executed or obsolete.
  • When a custom persona is added, it is a markdown file in src/roles/ with frontmatter and a lenses list in the body, not a code change; run pnpm census afterwards.
  • Keep prose English, American spelling (enforced by en-english-only-prose).
  • Git hooks live in .githooks/ and are installed by pnpm install (via prepare), or on demand with pnpm hooks:install. What lands in .git/hooks/ is a shim that executes the tracked hook, so the two cannot drift; pnpm hooks:check fails when a clone is missing them.
