# 068: Nothing the server starts outlives it: one shutdown path, an orphan guard, and idle memory release

- **Date**: 2026-09-02
- **Status**: accepted
- **Tags**: architecture, lifecycle, process, memory, transport
- **Author**: Emiliano Pisu <emiliano.pisu@rule.com>

## Context

Two stdio servers were found on a developer machine reparented to init, each spinning at 100% of a core for thirty-six minutes and holding 165 MB. A `sample` of the stack showed an uncaught exception on every event-loop check phase: the peer socket had no other end, every read errored, `installProcessErrorHandlers` logged and returned, and V8 formatted a fresh stack trace each time round. The SDK's stdio transport listens for `data` and `error` on stdin and nothing else - no `end`, no `close` - so nothing ends the process when its client goes away, and the `data` listener keeps stdin referenced so it cannot end on its own. Three more leaks were found beside it: `daemon start` never returned, because the parent held the detached daemon's stdio pipes; `daemon stop` deleted the pid file after a single SIGTERM, so a daemon that ignored it kept the port and lost the only record of its pid; and `serve --transport sse|http` waited on a promise that could never settle, with no signal handler, so a kill closed no session and flushed no buffer. Memory had no release path either: a shared daemon held the BM25 index over every skill (section text verbatim as well as tokenized), an LRU of SKILL.md bodies and 500 cache entries for as long as the process lived, and every session's MCP Server instance was pinned by a module-level variable that each new session overwrote. An earlier attempt at a SIGTERM handler in core/telemetry had hung the test suite, which is why none existed.

## Decision

Add one shutdown path and make every other lifecycle concern register with it. `core/lifecycle` holds a cleanup list, a tracked-child set and the signal handlers; each handler runs the cleanups behind an unref'd three-second deadline and then exits unconditionally (128 + signal), so a handler can never make the process harder to kill, and a second signal skips the cleanups. `serve` awaits `whenShutdown()` instead of a promise that never settles; the transports register their own stop. `transport/stdio-guard` ends the process when stdin closes, when a write fails with a dead-peer code, or when the parent becomes init, and never logs on that path because writing the diagnostic is part of what spins. `installProcessErrorHandlers` counts what it swallows and exits 70 past a hundred errors in a second. `transport/session-registry` replaces the plain Maps in both HTTP transports: it bounds sessions, closes them on the transport's callback, and sweeps for streams already destroyed or sessions idle for an hour. `core/reclaim` drops the index, the skill LRU and the in-memory cache tier after ten minutes of silence, flushing the cache to disk first so the next lookup reloads rather than recomputes. `server.js` tracks live Server instances in a Set. `daemon start` logs through an inherited descriptor instead of a pipe; `daemon stop` escalates SIGTERM to SIGKILL and removes the pid file only when the process is gone. Every child process gets a timeout and `killSignal: SIGKILL`, prettier is invoked directly rather than through `pnpx` so the deadline applies to the process it started, and the self-update git is tracked so a fetch cannot outlive the server.

## Consequences

A killed client no longer leaves a spinning orphan; the daemon starts without a second process babysitting its pipes and stops for certain; an idle daemon gives back the ~100 MB of rebuildable heap it was holding. The first call after an idle period pays a rebuild of the search index, and the first lookup after a release pays a read of the cache file - milliseconds, and no answer changes. The error-storm exit is a policy choice: a process that cannot make progress ends rather than burning a core, and a client that respawns its server sees a restart instead of a hang. `stopDaemonProcess`, `uninstallDaemonService` and `daemonCommand` became async, because waiting synchronously (Atomics.wait) both blocks the caller's event loop and stops the runtime reaping a child it spawned, which made every stop escalate to SIGKILL. Two test suites were added; three of their cases fail against the previous code and pass now, and the fourth - a peerless socketpair - is a regression guard rather than a proof.
