# 050: Retire the rules directory and move what was unique into the skills

- **Date**: 2026-08-31
- **Status**: accepted
- **Tags**: skills, documentation, guardrails, i18n, cleanup
- **Author**: Emiliano Pisu <emiliano.pisu@rule.com>

## Context

`rules/` arrived with a port from a sibling project and never connected to anything: ten files, 598 lines, and no code path that reads them - not the server, not a tool, not the installer. What it was instead was a second body of normative documentation running beside the skills, and a second body of normative documentation does not stay in sync with the first. Roughly 450 of those lines repeated a skill, often less well than the skill did. The remainder had drifted, and one line had drifted into a contradiction: `rules/typescript.md` told a reader to reach for `const enum` where an enum was unavoidable, and the `ts-union-over-enum` guardrail added in P3 fails on exactly that, `const` included. Two normative documents in one repository disagreeing is a tidy-up item right up to the moment one of them is executable, and then it is a defect: the reader who follows the document fails the check, and neither artifact tells them which one is wrong. The entry point of the set, `rules/common.md`, made the disconnection plain - it instructs an agent to call `get_skill` and `get_rule` on an MCP server this project does not run, and to scaffold from `scaffolding-*` skills that do not exist here.

## Decision

Retire the directory, and move what was genuinely unique before deleting it rather than after. Four things were unique and one of them was a real gap: there was no internationalization skill at all, so `rule-styleguide-i18n` is new - externalising strings without splitting sentences, semantic keys, plural and gender categories through `Intl.PluralRules`, dates, numbers, currencies and units through the rest of `Intl`, logical properties and `dir` for right-to-left, a pseudo-localization pass, and CI extraction. The required sections of an internal README join `rule-styleguide-readme`, which said how to write a README and not what has to be in one. OAuth 2.0 flow selection, the four conditions an API key is safe under, and the logging and alerting standards join `rule-backend-security`, which already covered rate limiting, CORS, headers, JWT and secrets. The `satisfies` operator joins `rule-styleguide-typescript`, where the enum section now states that the guardrail fails on `const enum` too and that keeping one is a written waiver, not a silent judgment call. Two smaller preservations surfaced while verifying the coverage claims rather than trusting them: the Expo exception to the Vitest-only rule existed in no skill, and now sits in both `rule-devops-testing` and `rule-platform-expo`; branch naming and merge-request conventions existed nowhere, and now sit in `rule-toolchain-commits`, which is where `rule-process-feature-workflow` was already pointing readers who would not have found them. The migration analysis preserved in `docs/03-engineering-guides.md`, which had described this move for months without performing it, goes with the directory.

## Consequences

One guardrail and one document no longer disagree, and `test/skills-docs.test.mjs` pins that: `const enum` may be named only on a line that also names the guardrail rejecting it, and `rules/` must not come back. The corpus gains a skill and the tool surface gains about 160 tokens on every turn, which fits inside the existing budget with roughly 60 to spare - R4 adds two more skills and will have to raise the budget deliberately or trim first. The routing corpus gains four i18n prompts. What is lost is the bootstrap material in `common.md`: the identity rules and the production-ready principle are superseded by the session directive and the installer, and the scaffolding index pointed at skills this project does not have. The general rule this records is the one worth keeping: parallel normative documentation drifts, and the copy nobody executes is the copy that goes stale.
