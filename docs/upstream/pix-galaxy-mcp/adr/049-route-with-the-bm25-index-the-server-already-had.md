# 049: Route with the BM25 index the server already had

- **Date**: 2026-08-30
- **Status**: accepted
- **Tags**: routing, bm25, search, quality, measurement
- **Author**: Emiliano Pisu <emiliano.pisu@rule.com>

## Context

Routing was scored by hand: per prompt word, take the best-scoring section, weight a heading match three times a body match, add a bonus if the word is in the skill description or equals the skill name, sum across words. No IDF, no stemming, no length normalization. The failures across three phases of adding skills all pointed the same way. A common word outranked a rare one, so "aspect ratio for video thumbnails" went to the accessibility skill, which owns "video", over the CSS skill, which owns "aspect ratio". The recurring false positives were the largest files - a11y at 24 KB, data-mysql at 17 KB, platform-desktop at 31 KB - because nothing normalized for length. A camelCase identifier was one token, so a section headed IntersectionObserver could not be reached by searching for either word. Meanwhile src/core/bm25.js already existed with proper IDF and length normalization, already indexed every section, and was already used by pix_search and by mode=tldr. There were two scoring systems and the router used the unprincipled one.

## Decision

Measure first, as P7 taught. test/routing-corpus.mjs collects 47 real prompts from the spot checks run while adding skills, plus the framework-bias cases already pinned elsewhere; the hand-rolled scorer scored 74% exact and 94% top-or-alternative. Then route through BM25, with four changes to the index. Compound identifiers are split at tokenize time and emitted alongside the whole token, so IntersectionObserver indexes as itself plus intersection and observer. Stemming is plural and third person only, because an over-stemmer creates false matches that are harder to debug than the misses it fixes. Section headings are indexed at three times weight, having previously not been indexed at all - a term appearing only in a heading scored zero. And a new searchSkills aggregates sections into one score per skill: the best section in full plus a diminishing share of the rest, multiplied by the fraction of query terms that skill actually contains. Two signals BM25 structurally cannot see are added back on top: naming the skill, and matching a curated frontmatter tag. Everything downstream is untouched - the framework bias, the confidence and uncertain outputs, and the JSON contract.

## Consequences

87% exact and 100% top-or-alternative, with no prompt left unable to reach its skill. test/routing-corpus.test.mjs holds a floor at 80% and 95%, deliberately below where the scorer sits so an ordinary skill edit does not fail the build, plus the assertion that matters most: nonsense stays uncertain, because a scorer that always answers cannot be trusted when it does. Coverage weighting is what made that work - raw BM25 ranked the one skill containing "jwt" in an example above the skill documenting JWT, because IDF makes a term appearing in a single document enormously valuable, which is right for search and wrong for routing. Two things surfaced that were not the scorer. "Best practices" is a section-title cliche appearing in dozens of headings, and the new heading boost amplified it into the dominant signal, so those words joined the stopword list. And the simplicity skill began winning plain build requests on content, since its over-engineering catalog legitimately discusses tables and migrations; it is a meta-skill about whether to build, so it is now damped unless a reduction signal is present, and the signal list gained the same question asked forward ("should I extract") rather than only as a complaint. The old scoreSkill is deleted rather than left beside its replacement.
